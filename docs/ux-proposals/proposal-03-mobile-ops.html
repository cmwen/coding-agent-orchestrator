Design 03: Responsive Ops Board

A desktop-and-mobile orchestration system built around a visible active session, a faster task queue board on mobile, and a calmer multi-pane desktop workspace. This spec now tracks the current product behavior closely so implementation can move forward without regressing existing functionality.

Design goals

  • Keep the current session-scoped orchestration model intact.
  • Reduce cognitive load by separating authoring, monitoring, review, and automation surfaces.
  • Add faster desktop power-user navigation through a command palette.
  • Turn mobile Home into a real queue board instead of a compressed desktop shell.
  • Preserve all existing behaviors: session continuation, queue actions, tmux output, diff review, and schedule CRUD.

Primary layout model

Desktop

Left session rail + resizable main workspace with tabs for Delegate, Terminal, Queue, Changes, and Schedules.

Mobile

Active-session header + Home queue board + bottom navigation for Delegate, Terminal, Changes, and Settings.

Keyboard layer

Desktop command palette (Cmd/Ctrl + K) for switching sessions and jumping to high-value actions without expanding the UI.

No-session behavior

Delegate, Terminal, and Changes only operate on the selected orchestrator session. If none is selected, all entry points must redirect to create/select session rather than dispatching work ambiguously.

Behavior parity with the current app

  • Session selection remains primary. The design does not replace the selected-session model with cross-session aggregation.
  • Provider continuation stays supported. Existing coding-agent session IDs still exist in session creation and settings, but can be collapsed as advanced fields in the new UX.
  • Delegate remains session-scoped. Prompt, one attachment, model/mode context, and optional per-task continuation override stay available.
  • Terminal remains tmux-backed. Reconnect state, send input, submit line, load older output, cancel current job, and new tmux session must remain visible somewhere in the flow.
  • Queue semantics stay accurate. One running job plus queued, failed, and completed history; retry/remove/continue actions are preserved. The design should not imply drag-reordering unless implementation changes.
  • Schedules remain CRUD-based. Editing includes frequency, timezone, weekly/monthly timing, email delivery, optional custom agent override, pause/resume, delete, and status summaries.

Desktop interaction contract

Session rail

Shows session title, provider, model, execution mode, and current continuation target. Supports session switching and entry to session settings.

Command palette

Scope: create session, switch session, open Queue/Changes/Schedules, focus delegate composer, retry latest failed job, and focus terminal.

Main tabs

Delegate, Terminal, Queue, Changes, and Schedules stay visible as first-class panes instead of one long scrolling column.

Diff review

Changes becomes a persistent workspace tab with loading, error, clean-working-tree, and text/binary diff states.

Mobile interaction contract

Home = queue board

Running, queued, failed, and scheduled work are organized into a queue-centric board. This is where mobile users inspect and manage task state.

Session picker

Mobile must expose a visible selected session and a quick switch pattern. Home owns this responsibility.

Delete queued work

Use swipe-to-reveal or inline delete actions, but document the affordance explicitly and preserve current remove behavior.

Bottom navigation

Home, Delegate, Terminal, Changes, Settings. Home handles queue oversight; Settings handles session defaults and schedules.

Create-session vs session-settings fields

Surface Fields that belong here
Create session Title, project path, provider, model, execution mode, required project purpose, optional project description, optional existing coding-agent session ID, optional first task.
Session settings Title updates, provider/model/mode defaults for future jobs, existing coding-agent session ID, custom agent, delete session, and clarifying copy that changes only affect future delegated jobs.
Delegate task Prompt, attachment, visible target session, model/mode visibility, and optional per-task continuation override.

State matrix

Surface Required states
Session selection active, available, missing, duplicate warning, create-first
Delegate ready, pending, disabled-without-session, validation error
Terminal idle, streaming, reconnecting, disconnected, load-more pending, load-more error
Queue running, queued, failed, completed, empty
Changes loading, clean, changed, diff error, binary/no-text diff
Schedules active, paused, empty, email error, edit modal, delete confirmation

Terminology

  • Active session: the currently selected orchestrator session that owns delegate, terminal, changes, and schedules.
  • Queue board: the mobile Home surface that summarizes running, queued, failed, and scheduled work.
  • Coding-agent session ID: optional provider-specific continuation target used by Copilot, Gemini, Codex, or OpenCode.
  • Project purpose: the required current field that captures the session objective and can later seed a richer system prompt.
